# Accounting machine SDK contract pin

These three product clients cover **all 80** customer machine operations in the production Accounting catalog and only the **12** synthetic operations in the isolated test catalog. The catalog count is derived from `operationId` values, not manually curated. They do not call the human Console, internal APIs, provider callbacks, or webhook delivery endpoints.

Existing published v0.1.1 artifacts keep their original source pins and do not contain the new banking methods.

The two hash-pinned public catalog files are vendored in `sdk/contracts` so SDK generation does not depend on private repository access. `generate.py` verifies both hashes before regenerating operation descriptors, TypeScript schema/request/result types, Python TypedDicts and named methods, and Go named wrappers. The Go schema/client model is regenerated with the repository-pinned `oapi-codegen v2.8.0`; its runtime `v1.7.0` and nullable `v1.2.0` match the Accounting service. All three were checked against their official GitHub latest releases on 2026-10-15. Do not edit generated files manually.

`go test ./sdk` compares every public operation and referenced component to the current runtime OpenAPI, allowing only the catalog's documented security-scheme narrowing and test-origin rewrite. Negative regressions reject the previous eight- and nine-grant limits and missing banking operations. Four explicit banking scopes correspond to four new local permissions; AccessPermissions supports thirteen unique grants without implicit assignment. All 24 banking methods are production-only, with source-bound intake and explicit reconciliation; provider authorization and synchronization are outside this API. `closeFiscalYear` declares both `accounting.periods.close` and `accounting.write`; both scopes and corresponding local permissions are required before idempotency replay. The isolated test contract continues to expose only its twelve synthetic operations and excludes closing. This is a local contract/source refresh; the published Accounting v0.1.1 and shared auth v0.1.0 retain their original source pins. This refresh adds banking schema types and named methods in all three local SDKs; existing distributed artifacts do not contain those methods. The historical public Go v0.1.0 is untouched.

The clients select only the canonical production resource `https://api.d0.eu/accounting` or isolated test resource `https://api.test.d0.eu/accounting`, with `/v1` for HTTP. The shared machine transport from `d0-auth` commit `427beab15ee4ba6d6487a85120d920f028a1cee5` owns private-key JWT, DPoP proofs, nonce retry, token refresh, HTTPS and redirect rejection. The canonical Go distribution paths are `github.com/dev-null-GmbH/d0-sdk/accounting/go` and `github.com/dev-null-GmbH/d0-sdk/auth/go v0.1.0`; the local Go replace plus npm/Python source overrides make qualification reproducible in this sibling workspace. Version 0.1.2 is the additive banking distribution candidate. **Do not republish v0.1.1 or claim this refresh is distributed.** A future public `d0-sdk` release must import the new pins, remove local overrides and qualify every artifact. Never place signing keys in browser code.

Create the client for one profile and one `ten_` public tenant ID. An empty tenant is accepted only for `listTenants`/`createTenant` onboarding. Every mutation takes a caller-owned `Idempotency-Key` of 16–128 safe characters; preserve it on retry. `If-Match` values are passed through unchanged, with Go exposing the generated response headers and TypeScript/Python exposing the latest ETag. Amounts remain exact decimal **strings** in minor units. Success bodies use generated schema types; failures expose bounded status, problem type/title, and request ID without raw problem detail. Binary responses have a 512 MiB bound; ordinary responses have a 24 MiB bound. List operations expose opaque `nextCursor` values and bounded page helpers; asynchronous status reads have at-most-two-minute polling helpers. The fixtures create two accounts, an open period, and an unposted balanced draft in both profiles. They never post a Buchung or reach a live service.
